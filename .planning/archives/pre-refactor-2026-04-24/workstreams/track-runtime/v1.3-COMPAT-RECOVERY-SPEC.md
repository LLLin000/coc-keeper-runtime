# v1.3 Compatibility & Recovery — Design Specification

**Status:** Draft → Decisions Recorded
**Created:** 2026-04-03
**Updated:** 2026-04-03

## Core Problem

After v1.0-v1.2, runtime semantics must not drift. New modules, longer campaigns, and restart paths will erode contracts unless formalized.

---

## Design Principles

> **Overarching rule:** System detects, records, proposes; KP/player authorizes at key decision points.
>
> **Migration philosophy:** Additive-first; load-time migration; preserve replay/test assets.

---

## Module/Runtime Compatibility Contract

**D-10: Migration Strategy — Additive-First + Load-Time Migration**

```
Schema evolution rules:
1. Default: additive changes only (new fields, new optional fields)
2. Breaking changes: only at major version boundaries (v2.0, v3.0)
3. Every version has explicit MigrationPath
4. Loading old save → auto-migrate to current schema

Migration requirements:
- Idempotent
- Testable
- Logged
- Reversible (rollback_fn where possible)
```

```python
class ModuleContract:
    module_id: str
    runtime_version: str           # e.g., "v1.0", "v1.1"
    required_capabilities: Set[str] # e.g., {"scene_fork", "reveal_gates"}
    optional_capabilities: Set[str]
    field_schema: dict             # which runtime fields this module reads/writes
    
    def validate(runtime_capabilities) -> CompatibilityResult

class RuntimeStateV1:
    schema_version: str = "v1.0"
    scenes: Dict[scene_id, SceneStateV1]
    focus_scope: Dict[player_id, scene_id]
    knowledge: Dict[player_id, PlayerKnowledgeState]
    trigger_chains: List[TriggerChainState]
    audit_log: List[AuditEntry]
    
class MigrationPath:
    from_version: str
    to_version: str
    migrate_fn: Callable[[dict], dict]
    rollback_fn: Callable[[dict], dict] | None
```

**Compatibility levels:**
- `FULL` — all required capabilities supported
- `PARTIAL` — some required missing, graceful degradation
- `INCOMPATIBLE` — cannot run

## Compatibility Checkpoints

**D-11: Compatibility Check Timing — Three-Layer Strategy**

```
Layer 1: Module load time (static)
- Schema compatibility
- Required/optional capability check
- Required field presence
- Registration conflicts

Layer 2: Session start (combinatorial)
- Enabled modules work together
- No capability conflicts between modules

Layer 3: Resume (strictest)
- All checkpoint_ids resolve to valid savepoints
- No poisoned state from previous session
- Integrity check passes before preload
```

**Why three layers:** Different failure modes at each stage; resume is most critical (old state with new code is highest risk).

## Placeholder Cleanup Strategy

**D-12: Placeholder Cleanup — Correctness-Critical First**

```
Priority order:
1. Critical (must fix before v1.0 release):
   - MessageBuffer edge cases with round-robin
   - TurnCoordinator sequential submission assumption
   - eventual consistency in session state sync

2. High (blocks recovery/triggers):
   - Placeholder runtime logic in gameplay code

3. Medium (code quality):
   - main.py duplicate initialization (lines 124-158)
   - Fuzzy profile selection vs campaign binding boundary

4. Low (deferred):
   - Missing docstrings
   - No formal deprecation policy
```

**Why not all CONCERNS.md at once:** Some concerns are not blockers, just "design TBD." Completing correctness-critical first is more practical than completeness theater.

## Integration Test Coverage

**D-13: Integration Test Scope — Happy Path + Key Failures + Representative Cases**

```
Minimum v1 coverage:
- One ordinary trigger success flow
- One reaction rollback (atomicity test)
- One blocker suspend/resume
- One reveal gate: private → shared
- One scene fork → switch → merge
- One migration from N-1 schema
- One resume after checkpoint

NOT in v1 scope:
- All trigger type × all scene transition combinations
- Performance/load testing
```

## Key Decisions Summary

| Decision | Choice | Rationale |
|----------|--------|-----------|
| D-10: Migration | additive-first + load-time migration | Preserves test/replay assets; avoids breaking changes |
| D-11: Compatibility check | 3-layer: load + session + strict resume | Different failure modes at each stage |
| D-12: Placeholder cleanup | correctness-critical first | Complete vs practical; don't fix design-TBD as blockers |
| D-13: Test coverage | happy path + key failures + representative | Full combination explodes; representative is sufficient |
