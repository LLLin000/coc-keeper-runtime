# v1.1 Trigger & Blocker Runtime — Design Specification

**Status:** Draft → Decisions Recorded
**Created:** 2026-04-03
**Updated:** 2026-04-03

---

## Core Problem

Current trigger system applies effects inline and treats blockers (clarifications, pending rolls) as side effects. Complex module behavior is hard to reason about and harder to recover.

---

## Design Principles

> **Overarching rule:** System detects, records, proposes; KP/player authorizes at key decision points.

---

## Trigger Event Entry Contract

```python
class TriggerEvent:
    trigger_id: str
    scene_id: str
    source: Literal["player_action", "time_elapsed", "condition_met", "manual"]
    predicate: TriggerSpec          # from v1.0 spec
    context: dict                   # world_state snapshot at trigger time
    status: Literal["pending", "running", "blocked", "completed", "failed"]
    checkpoint_id: str | None       # for resumption
```

## Reaction Classification

**D-01: Reaction Execution Order**
```
reaction_order = sort(priority desc, registration_order asc, id asc)
```
- Primary: `priority` (KP-defined)
- Secondary: `registration_order` (stable, prevents hash opacity)
- Tertiary: `id` (deterministic tiebreaker)
- **Not used:** pure deterministic hash (black box, hard to explain to KP)

```python
class ReactionSpec:
    reaction_type: Literal["narrative", "mechanical", "composite"]
    priority: int                  # execution order (KP-assigned)
    registration_order: int        # auto-incremented, stable
    conditions: List[TriggerSpec]  # pre-conditions
    effects: List[Effect]
    blockers: List[BlockerSpec]    # what can interrupt this
```

**D-02: Effect Atomicity**
- **Reaction-level transaction:** effects within a single ReactionSpec are atomic (all succeed or all rollback)
- **Multi-reaction execution:** serial — previous reaction commits before next runs
- **Why not:** global transaction (complex with blockers/choices/dice), single-effect independence (leaves dirty state)

```python
class Effect:
    target: Literal["scene", "player", "world"]
    field: str                     # e.g., "SAN", "scene.local_state.darkness"
    operation: Literal["set", "delta", "roll", "apply"]
    value: Any
```

## Blocker Checkpoints

**D-03: Blocker Resolution Strategy**
```
semi-manual by default:
1. Player-choice blockers → Player decides
2. Judgment blockers → KP decides
3. Explicitly declared auto-resolvers → System auto-resolves (e.g., public dice, fixed DC, unambiguous table)
4. timeout → does NOT auto-resolve; marks as "suspended" / "requires_attention"
```

Blocker taxonomy:
```python
class BlockerSpec:
    blocker_type: Literal["choice", "judgment", "auto", "external"]
    description: str               # human-readable for KP
    required_resolution: Any       # e.g., roll outcome, player choice
    timeout: int | None            # in turns, or None
    
    # Resolution states (not blocker types):
    # resolved, suspended, escalated
```

**Why not timeout-as-resolution:** timeout is not a resolution, it's abandonment.

---

## Checkpoint Strategy

**D-04: Checkpoint Granularity**
```
Two checkpoint types:
A. Event checkpoint: before entering each TriggerEvent
B. Blocker checkpoint: when a blocker requiring human input is encountered
```
- Not per-effect (too fine, storage bloat)
- Not only at blocker (less safe than event-level)
- Resume semantics: return to event start, or continue from blocker

## Resumable Trigger Chains

```
TriggerChain:
    chain_id: str
    events: List[TriggerEvent]
    current_index: int
    blocked_at: BlockerSpec | None
    audit_log: List[AuditEntry]
    
    resume()
    ├── Restore savepoint
    ├── Re-evaluate blocker conditions
    └── Continue from resume_from
    
    checkpoint()
    ├── Serialize current state
    └── Store to PersistenceStore
```

## Key Decisions Summary

| Decision | Choice | Rationale |
|----------|--------|-----------|
| D-01: Reaction order | priority -> registration_order -> id | Controllable, explainable, replayable, test-stable |
| D-02: Effect atomicity | reaction-level transaction | Balances safety vs complexity; avoids dirty state |
| D-03: Blocker resolution | semi-manual by default | KP/player control; auto only for explicitly declared |
| D-04: Checkpoint granularity | per TriggerEvent + per blocker | Balanced safety vs simplicity |
