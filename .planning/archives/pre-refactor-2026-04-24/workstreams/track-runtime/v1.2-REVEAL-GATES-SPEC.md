# v1.2 Reveal Gates & Knowledge Ownership — Design Specification

**Status:** Draft → Decisions Recorded
**Created:** 2026-04-03
**Updated:** 2026-04-03

## Core Problem

Private and shared information flow is currently enforced by narrative discipline, not runtime rules. Knowledge ownership is not explicit.

---

## Design Principles

> **Overarching rule:** System detects, records, proposes; KP/player authorizes at key decision points.

---

## Reveal Gate Model

**D-05: Clue Creation — Hybrid Workflow with Canonical Confirmation**

```
Two-layer model:
- candidate_clue: AI extracts from narrative (not authoritative)
- canonical_clue: KP/validator confirms before entering registry

Why not direct AI-to-canonical:
- Narrative often contains atmosphere, hints, AI embellishments
- Direct入库 pollutes reveal gates with unverified content
```

```python
class RevealGate:
    gate_id: str
    content: Any                    # clue, info, item, secret
    owner: player_id | "kp" | "table"
    visibility: Literal["private", "kp_only", "shared", "revealed"]
    unlock_condition: TriggerSpec | None
    revealed_at: datetime | None
    reveal_history: List[RevealEvent]
    
    # Lifecycle:
    # candidate → (KP confirm) → canonical → (unlock) → revealed
```

**D-06: KP-Only Information Presentation**

```
Player side:
- Cannot see specific content
- Does NOT automatically see "[REDACTED]" or similar markers
- Optional: abstract placeholder only if design explicitly requires "you know something exists"

KP panel:
- Owns full secret content
- Can view, edit, override any reveal gate

Why not [REDACTED]:
- Already meta-games: reveals secret exists, approximate count, location/event
- Especially problematic for horror/investigation genres
```

```python
class RevealEvent:
    gate_id: str
    revealed_to: Set[player_id]
    triggered_by: player_id | "system"
    timestamp: datetime
```

## Clue Ownership & Scope Transitions

**D-07: Clue Scope Expansion — Explicit + Auditable, Not Arbitrary IC**

```
Knowledge gain modes (in priority order):
1. explicit_share:     Player voluntarily shares
2. shared_co_present:  All participants witness same public event (e.g., public statement, shared observation)
3. shared_by_kp:       KP explicitly expands scope
4. NOT arbitrary_IC_action: Any IC action does NOT automatically propagate knowledge
```

```python
class Clue:
    clue_id: str
    content: str
    source_scene_id: str
    ownership: Literal["kp", "investigator"]
    scope: Set[player_id]           # who currently knows this clue
    knowledge_gain_mode: Literal["explicit_share", "shared_co_present", "shared_by_kp"]
    reveal_gates: List[str]         # gates that must open to reveal this
    
    def scope_expand(self, players: Set[player_id], mode: str)
    def scope_transfer(self, from_: player_id, to: player_id)
```

**Why not arbitrary IC propagation:** Ambiguous, hard to audit, easy to leak knowledge accidentally.

## NPC Knowledge Model

**D-08: NPC Knowledge — Lightweight Separate Model**

```
NOT a full PlayerKnowledge clone.
NPC does not need reveal/secrecy semantics designed for players.

Two-component model:
- NPCFactsKnown: what this NPC knows (lightweight)
- NPCDisclosurePolicy: under what conditions NPC reveals knowledge

Rationale:
- Full PlayerKnowledge for NPCs is overweight
- Reveal/secrecy semantics don't translate directly
- Keeps "NPC knowledge" separate from "NPC disclosure"
```

```python
class NPCKnowledge:
    npc_id: str
    known_facts: Set[str]           # fact IDs, not full content
    disclosure_policy: List[DisclosureCondition]
    
class DisclosureCondition:
    trigger: str                    # e.g., "player_mentions_X", "roll_skill_check"
    revealed_facts: Set[str]
    requires_kp_approval: bool
```

## Secrets Permanence

**D-09: Secrets — Private by Default, Reveal by Condition, No Auto-Expiry**

```
Default: private_forever (never expires by time)

Better model:
- reveal_on_condition: triggers when specified condition met
- reveal_on_share: player voluntarily shares
- reveal_on_scene_merge: when relevant scene merges
- reveal_on_kp_override: KP explicitly reveals

Why not time-based expiry:
- Secrets in investigation narratives don't "go bad" like milk
- Auto-expiry creates bizarre narrative situations
- Resume/resume would need to track expiry timers
```

```python
class Secret:
    secret_id: str
    content: str
    owner: player_id
    reveal_policy: Literal["never", "on_condition", "on_share", "on_scene_merge", "on_kp_override"]
    reveal_condition: TriggerSpec | None
```

## Table vs KP Visibility

```
Table-visible consequences:
- Scene resolved, all participants see outcome
- Shared clues now in shared scope
- Public narrative

KP-only information:
- Private clues of individual players
- SAN checks and outcomes
- NPC knowledge not yet revealed
- Plot seeds not yet deployed
- KP panel content is never player-visible unless explicitly revealed
```

## Key Decisions Summary

| Decision | Choice | Rationale |
|----------|--------|-----------|
| D-05: Clue creation | AI candidate + canonical confirmation | Prevents unverified content from polluting registry |
| D-06: KP-Only presentation | hidden by default, KP panel owns full | [REDACTED] meta-games; horror requires true concealment |
| D-07: Scope expansion | explicit / co-present / KP override only | Arbitrary IC propagation too ambiguous, hard to audit |
| D-08: NPC Knowledge | lightweight separate model | Full PlayerKnowledge is overweight; different semantics |
| D-09: Secrets permanence | private by default, no time expiry | Time expiry creates narrative absurdities; condition-based better |
